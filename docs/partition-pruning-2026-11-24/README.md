## Изменение

В [get_activity](../../backend/app/services/library_service.py) и [list_comments](../../backend/app/services/community_service.py) к существующему условию добавлена явная граница по ключу партиционирования:

```sql
created_at <= :cursor_created
AND (created_at, id) < (:cursor_created, :cursor_id)
```

Это эквивалентно прежнему tuple-условию при NOT NULL created_at/id: оно уже подразумевает `created_at <= cursor_created`. Скалярное условие делает границу доступной partition pruning. `<=` принципиально сохраняет строки с одинаковым временем и меньшим ID; заменять его на `<` нельзя. Tuple-предикат по-прежнему обеспечивает строгую границу следующей страницы.

Сортировка `(created_at DESC, id DESC)`, limit+1, формат курсора и ответы API не менялись. На первой странице, где курсора нет, нового условия нет. Миграции/индексы, range-фильтр годов, auth и код PR #15 не менялись. Общий стенд не использовался.

## Регрессии

Добавлен [test_partition_pruning.py](../../backend/tests/unit/test_partition_pruning.py): два эндпоинта × четыре размера страницы (1, 2, 3, 20) = **8 случаев**.

Для каждого случая:

- 9 строк с тремя группами одинаковых timestamp, порядок вставки смешанный относительно даты;
- реальные две месячные партиции активности / две годовые партиции комментариев, DEFAULT для данных фикстуры не используется;
- timestamp точно на границе, на секунду позже и на микросекунду раньше;
- проверка каждой страницы против полного ожидаемого порядка `(created_at,id) DESC`, отсутствие пропусков и дублей, корректные first/last/empty pages;
- проверка decode существующего next_cursor против последней строки страницы;
- EXPLAIN реального SELECT сервиса после последней строки: новая физическая партиция отсутствует в плане.

В месяцах, когда стандартный трёхмесячный горизонт миграции ещё не создаёт следующий год, тест при необходимости вызывает штатную ensure_partitions(12) внутри своей откатываемой транзакции. Поэтому межгодовая проверка не зависит от даты запуска.

## Фактические EXPLAIN до/после

На одной отдельной БД применены существующие миграции и добавлены синтетические данные — по 9 строк на эндпоинт в двух реальных партициях, включая непустую будущую партицию. Dataset и настройки: [dataset.json](dataset.json). enable_seqscan=on; принудительные настройки planner не использовались. Это небольшой набор для проверки pruning, не нагрузочный тест.

Baseline импортирует **исходные сервисы из git archive base commit**, after — изменённые сервисы. Перехвачен фактический SQL SELECT страницы, он выполнен с реальными параметрами через EXPLAIN (ANALYZE, BUFFERS). Текст/JSON снимались отдельными выполнениями, поэтому их тайминги могут отличаться.

| Курсор | Активность: партиций в плане до → после | Комментарии: до → после | Корректность |
|---|---|---|---|
| Первая страница, без курсора | 5 → 5 | 3 → 3 | Те же ID и next_cursor; запрос не изменён |
| Точно граница новой партиции, середина группы одинакового времени | 5 → 3 | 3 → 3 | Партиция с timestamp=cursor_created сохранена, строки с меньшими ID не потеряны |
| Курсор в старой партиции | **5 → 2** | **3 → 2** | Исключены 3 будущие месячные / 1 будущая годовая; те же ID и next_cursor |

DEFAULT остаётся допустимой, поскольку в общем случае может содержать более старые строки. На зафиксированном межгодовом наборе комментариев при курсоре на границе 2027 года следующей явной партиции 2028 ещё нет; поэтому количество отношений для этого случая не меняется. Это не отсутствие pruning на более старом курсоре: в следующем случае 2027 действительно исключена.

[Сравнение результатов и исключённых партиций](comparison.txt), [планы до: текст](plans-before-pg16.txt) / [JSON](plans-before-pg16.json), [планы после: текст](plans-after-pg16.txt) / [JSON](plans-after-pg16.json).

Воспроизведение на **отдельной пустой одноразовой БД**:

1. Применить существующий `alembic upgrade head` с локальным DATABASE_URL из окружения.
2. Задать REVIEW_DATABASE_URL этой же БД вне репозитория и выполнить [prepare_dataset.py](prepare_dataset.py) (создаёт синтетические строки, выполняет ANALYZE).
3. Экспортировать backend исходного base commit в отдельный каталог через git archive; запустить [capture_plans.py](capture_plans.py) с аргументом `before`, PYTHONPATH указывает на baseline backend.
4. На той же неизменённой БД повторить с аргументом `after`, PYTHONPATH указывает на изменённый backend. Скрипт вызывается из backend либо с абсолютным PYTHONPATH.
5. Сопоставить ID/next_cursor и Relations в JSON. Снимки из этого отчёта уже содержат фактические параметры. Пароли/DSN в evidence не сохраняются.
