## Антон (frontend) — интеграция с реальным API

В git уже лежит реальный backend: `POST /auth/register|login|refresh`, `GET /genres`,
`GET /anime`, `GET /anime/{id}` (примеры ответов — `docs/api.md`, разделы ✅).
По каждому эндпоинту там же написано, какие поля бывают `null` — это важно.

### A0. Поднять локальный контур (полчаса, один раз)

```bash
git pull
docker compose -f docker-compose.dev.yml up -d          # PostgreSQL + Redis
cd backend
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env                                    # значения подходят из коробки
alembic upgrade head                                    # схема
psql postgresql://anifolder:anifolder@localhost:5432/anifolder -f scripts/seed_dev.sql
uvicorn app.main:app --reload                           # порт 8000
```

Проверка: `curl localhost:8000/health` → `{"status":"ok"}`; в браузере `localhost:8000/docs` —
интерактивная спека, можно дёргать эндпоинты руками.
Твой `vite.config.ts` уже проксирует `/api` на `:8000` — менять ничего не надо,
`apiClient` ходит на `/api/v1` относительно твоего dev-сервера.

### A2. Auth-флоу end-to-end (`frontend/src/api/client.ts`, `store.ts`, формы)

1. **Интерсептор 401 — реальный refresh.** Сейчас на 401 только `console.warn`. Нужно:
   POST `/auth/refresh` с `refreshToken` из стора → записать новую пару в стор →
   повторить исходный запрос один раз.
2. **Одна очередь рефреша.** Пять параллельных запросов не должны дать пять вызовов
   `/auth/refresh` (бэкенд ротирует токен: первый вызов отзовёт токен, остальные четыре
   получат 401 `REFRESH_TOKEN_REUSED` и убьют сессию). Храни промис обновления:
   если рефреш уже идёт — все ждут его, а не стартуют свой.
3. **Неуспешный рефреш** (`INVALID_REFRESH_TOKEN`, `REFRESH_TOKEN_REUSED`, `EXPIRED`)
   → `logout()` → редирект на страницу входа. `REFRESH_TOKEN_REUSED` покажи отдельным
   сообщением: «Сессия отозвана, войдите заново».
4. **Ошибки форм.** 409 `USERNAME_TAKEN` / `EMAIL_TAKEN` → подсветить конкретное поле.
   422 `VALIDATION_ERROR`: в `details[]` есть `loc` (например `["body","password"]`) и
   готовое русское `msg` — показывай его, не изобретай свои тексты.
5. **429 `RATE_LIMITED`.** Покажи тост «Слишком много попыток, подожди минуту»
   (заголовок `Retry-After` есть, но пока всегда 60 — можно не парсить).
6. **Клиентская валидация пароля до отправки:** 8–72 символа. Бэкенд отрежет 73-й
   молча обрежет до 72 — лучше не допускать.
7. **Валидация username** на клиенте: `^[A-Za-z0-9_]{3,32}$` — та же регулярка, что в БД.

### A3. Каталог без моков (`frontend/src/api/anime.ts`, `catalog.ts`)

Сними `USE_MOCK` (или веди флаг из `.env`: `VITE_USE_MOCK=false` — как удобнее,
но по умолчанию после спринта — реальный API).

- `getAnimeList`: сигнатура та же; `search` уходит параметром, фильтрация на сервере.
  Мелочь: debounce 250–300 мс на поле поиска, не дёргай API на каждый символ;
  пустой search не отправляй (параметр не передаётся вообще, а не `search=`).
- `getAnimeDetails(id)`: ответ — `AnimeDetail` (добавились `description`, `genres`,
  `stats`). `stats.avg_score` приходит **строкой** (`"8.12"`) — парси в `float` для
  отображения; `stats` может быть `null` (показывай «оценок пока нет»).
- `getGenres`: `name_ru ?? name_en` при отображении — включая фильтры каталога.

### A4. Сценарии приёмки (прогнать руками, отметить галочки)

- [ ] Каталог: поиск «Test Anime», фильтры по жанру/статусу, пагинация — работают

## Сергей (ML) — Recommendation Service

Контур твой: каталог и оценки уже в БД (seed: 500 тайтлов, ~39k записей `user_anime`,
у ~430 тайтлов есть `mal_id` — для холодного старта по датасетам).
Внутренний API описан в README; граница с backend зафиксирована в `docs/api.md`
→ раздел «/me/recommendations»: **ML пишет таблицу `recommendations`, backend читает
и сам исключает просмотренное. Фильтрацию не дублируй.**

### S1. Скелет сервиса (`ml/`)

FastAPI, порт **8001** (8000 — backend). Конфиг БД — тот же `DATABASE_URL` из
`backend/.env`, но движок синхронный (SQLAlchemy sync + psycopg, либо psycopg напрямую) —
сервис не asyncio-нагруженный. Структура: `ml/app/main.py`, `ml/app/db.py`,
`ml/requirements.txt`, README «как запустить». Зависимости — минимальные, версии
фиксируй (как в backend).

### S2. Внутренний API (по README)

- `GET /internal/v1/recommendations/{user_id}?limit=20` →
  `200 [{"anime_id": 42, "relevance": 0.91}, ...]`, отсортировано по `relevance` DESC.
  Источник — таблица `recommendations` (пока там seed-заглушки `model_version =
'seed-popular'` — это нормально, выдавай как есть). `limit` ≤ 50, дефолт 20.
- `POST /internal/v1/train` → `202 {"status": "ok"}` с заглушкой «переобучение
  запланировано». Настоящий ALS — следующая итерация, см. S4.
- Сервис снаружи не публикуется (в compose — без проброса порта наружу, только
  в общую сеть; из интернета недоступен).

### S3. Холодный старт — первая реальная логика

По README: новым пользователям без оценок — популярные тайтлы из любимых жанров.
Алгоритм:

1. Жанры пользователя: берём его оценки ≥ 7 из `user_anime`, считаем частоту жанров
   этих тайтлов (через `anime_genres`), топ-3 жанра.
2. Если оценок с ≥7 нет — топ-3 жанров всего каталога.
3. Кандидаты: тайтлы этих жанров, `ORDER BY in_lists_count DESC LIMIT 50`.
4. Записать в `recommendations`: **удалить старые строки пользователя и вставить
   новые в одной транзакции** (договорённость `docs/database.md`),
   `model_version = 'cold-start-v1'`, `relevance` — нормированный ранг (1.0 … 1/n).
5. Метод вызывается из `POST /internal/v1/train` (пока это единственное, что train
   делает) — идемпотентно: повторный вызов даёт тот же результат.

Проверка: пользователь `user1` из seed имеет оценки — прогони train для него,
посмотри в БД, что записалось (psql: `SELECT * FROM recommendations WHERE user_id = 1`).

### S4. ALS-разведка (по оставшемуся времени, не блокер)

`ml/notebooks/`: на seed-матрице `user_anime (user_id, anime_id, score)` —
`implicit` ALS, holdout по времени, метрика map@10. Цель — понять, хватает ли
39k оценок для осмысленных рекомендаций или просим Федора расширить seed.
В проде обучение идёт с read-реплики и по расписанию раз в сутки — здесь реплики
нет, обучайся на primary, объёмы dev позволяют.

### Сдача

PR `[ml] recommendation service: skeleton, internal api, cold start` +
README «как поднять рядом с backend». Отдельно — одним абзацем: устраивает ли
формат записи `recommendations` и выдачи, или просишь что-то менять
(backend адаптируется сейчас, не потом).

## Никита (БД) — ревью + планы запросов

### N1. Планы запросов каталога

Готовый файл: `backend/scripts/query_plans.sql` — шесть запросов с
`EXPLAIN (ANALYZE, BUFFERS)` и пометками, что смотреть. Запуск на seed:
команды в шапке файла (нужен `pg_trgm` — он создаётся миграцией 0001).

- **Запрос 2 (поиск trgm):** ждём Bitmap Index Scan по `anime_title_en_trgm_idx`.
  Если Seq Scan — разбираем (варианты: статистика, ` similarity_threshold`).
- **Запрос 4:** `anime_genres` — Index Scan по PK; остальное — Bitmap по
  `anime_kind_aired_on_idx` или Seq Scan (зафиксируй, что выбрал planner).
- **Запрос 5 (фильтр по годам):** известное ограничение — `date_part('year',
aired_on)` не берёт индекс. Два пути: (а) backend меняет фильтр на range по
  `aired_on` (годы → даты 2010-01-01…2020-12-31, тогда работает часть
  `anime_kind_aired_on_idx` с kind-фильтром); (б) expression-индекс — это уже
  миграция 0002, твоя зона. **Выбери и напиши в тред — реализуем сразу.**
- Честности ради: 500 тайтлов — мало, выводы делаем по «индекс используется/нет»,
  не по таймингам. Масштабные выводы — после роста каталога из AniList (~20k).

### N2. Ревью backend-кода как клиента твоего слоя

Файлы: `backend/app/services/*.py`, `backend/app/workers/catalog_sync.py`,
`backend/app/models/*.py`. Смотрим:

1. Договорённости `docs/database.md` соблюдены: поиск через `lower()`,
   upsert по PK/`anilist_id`, `lazy="raise"` (подгрузка только `selectinload`),
   триггерные поля (`updated_at`, счётчики тем) приложением не пишутся.
2. Запросы без N+1: `list_anime` — 2 запроса (count + select), деталь тайтла —
   2–3 (сущность + жанры + stats).
3. Воркер синхронизации: `title_ru` при конфликте не обновляется, жанры —
   `ON CONFLICT (name_en) DO NOTHING`, связи пересобираются — так и задумано?
4. `tests/conftest.py` накатывает на тестовую БД реальный `alembic upgrade head` —
   проверь глазами, что миграция применяется чисто на пустой базе
   (после `DROP DATABASE anifolder_test`).

Замечания — issue с тегом `[db-review]`, спорные места обсудим в треде, не правим молча.

### Сдача

Выводы `query_plans.sql` (можно вывод целиком) — в тред; решение по запросу 5;
ревью-замечания — issue.
