### N2: подтверждённые проблемы, в порядке приоритета

**P1 — неверное направление словаря ID ломает импорт и синхронизацию жанров.** [catalog_sync.py:144–153](../backend/app/workers/catalog_sync.py#L144): RETURNING (Anime.id, Anime.anilist_id) и dict дают internal_id → anilist_id. DELETE использует values как внутренние ID, а создание links ищет ключ anilist_id. Воспроизведён KeyError 800000001 на отдельном тайтле; два штатных теста worker также падают с KeyError 1. Для существующего seed-тайтла id=1/anilist_id=900000001 пустой снимок genres=[] оставил 1 связь вместо удаления всех. Возможны ошибочные удаления чужих связей при совпадении внешнего ID с внутренним ID другого тайтла. Предложение: явно построить `{anilist_id: internal_id}` из RETURNING; значения использовать в DELETE, lookup по anilist_id — в links. Нужен регрессионный тест с заведомо различными ID и пустым снимком, а не только совпадающими 1/1. Исправление не внесено.

**P1 — курсор после частичного импорта пропускает необработанные записи.** [catalog_sync.py:58](../backend/app/workers/catalog_sync.py#L58) сортирует по ID, не updatedAt; [строка 270](../backend/app/workers/catalog_sync.py#L270) берёт максимум updatedAt уже обработанных страниц; [строки 281–285](../backend/app/workers/catalog_sync.py#L281) сохраняют его в finally при исключении. Воспроизведение run с фейками: старый курсор 100, страница 1 успешно применена (updatedAt=300), импорт страницы 2 падает (updatedAt=200), но Redis получает 300. Следующий updatedAt > 299 исключает необработанную запись 200. Перекрытие на секунду проблему не решает. То же воспроизведено с --max-pages=1 без исключения. Это не утверждение о сохранении курсора именно упавшей страницы: код обновляет максимум после успешного apply; опасен максимум предыдущих страниц при сортировке ID. Предложение: сохранять новый watermark только при доказанно полном успешном обходе; при ошибке/ограничении страниц оставлять старый. Для полного импорта нужен watermark, не теряющий изменения во время обхода. Также не трактовать GraphQL errors как успешную пустую страницу ([строка 262](../backend/app/workers/catalog_sync.py#L262)). Исправление требует согласования и тестов с ошибкой fetch/apply, ограничением страниц, отсутствием Redis и изменениями во время синхронизации.

**P2 — тестовая изоляция ломается после rollback сервиса.** [conftest.py:87–100](../backend/tests/conftest.py#L87) создаёт внешнюю транзакцию, но AsyncSession не получает join_transaction_mode='create_savepoint', вопреки обещанию в docstring. Воспроизведено: session.rollback() делает внешнюю tx inactive; последующий session.commit() сохраняет строку, которая остаётся после заявленного внешнего rollback. В реальном backend rollback есть в [auth_service.py:36](../backend/app/services/auth_service.py#L36) и [95](../backend/app/services/auth_service.py#L95). Предложение: явные savepoint и проверка изоляции после rollback+commit; backend/conftest не правились.

**P2 — небезопасный выбор цели тестового DROP.** [conftest.py:42–59](../backend/tests/conftest.py#L42) берёт host/port/credentials из пользовательского DATABASE_URL и без opt-in выполняет DROP anifolder_test WITH (FORCE), также при teardown. Название базы фиксировано, но сервер может оказаться общим. Перед обычным pytest требуется отдельный тестовый DSN и защитная проверка цели/явное разрешение удаления. Здесь DROP не выполнялся: обе команды отключены только в временной копии.

**P2 — неверное ожидание теста пагинации.** [test_catalog.py:78](../backend/tests/unit/test_catalog.py#L78): для пяти названий порядок Announced Title, Naruto, Naruto Movie, On Hold Title, Sasuke Future. Page=2/limit=2 корректно даёт Naruto Movie и On Hold Title; тест ждёт Naruto и Naruto Movie. Это дефект ожидания теста, не доказанная ошибка SQL-пагинации.

**P2 — нестабильное ожидание уникальности access JWT.** [test_auth.py:154](../backend/tests/unit/test_auth.py#L154) требует отличающийся access_token сразу после refresh. [security.py:36](../backend/app/core/security.py#L36) формирует детерминированный payload без jti; при выдаче в одну секунду токены могут совпасть, что и произошло. Ротация refresh в этом тесте не проверена до конца из-за раннего assert; другие auth-тесты прошли. Нужно согласовать контракт: уникальный access JWT или проверка обновлённого refresh без требования уникальности access. Это не доказательство сбоя ротации refresh в БД.

### N2: соблюдённые договорённости и границы ревью

- Username/email ищутся через lower в [auth_service.py:114](../backend/app/services/auth_service.py#L114), [119](../backend/app/services/auth_service.py#L119), [128](../backend/app/services/auth_service.py#L128); функциональные unique-индексы совпадают со схемой. Регистрация ловит IntegrityError гонки и повторяет проверку после rollback.
- refresh_tokens хранит SHA-256, не исходный токен; условный UPDATE revoked=false проверяет rowcount. У модели session expire_on_commit=False, чтение после commit не вызывает автоматический lazy refresh.
- Все три ORM relationship имеют lazy='raise'. Деталь использует selectinload(genres) и joinedload(stats): joinedload для одиночной связи не нарушает запрет неявной загрузки и экономит отдельный запрос.
- Вызовы сервисов измерены через SQLAlchemy event на реальной seed-БД: list limit=1 и limit=50 — **ровно 2 SQL**; деталь — **2 SQL**. Pydantic для карточек не читает отношения, N+1 в проверенных путях не выявлен. Сценарий 6 SQL-файла тоже содержит два EXPLAIN, несмотря на комментарий «три запроса».
- Upsert anime действительно на anilist_id, mal_id обновляется включая NULL. title_ru не включён в DO UPDATE; его сохранение подтверждено воспроизведением с пустыми жанрами. genre upsert на name_en DO NOTHING не меняет name_ru. Полная замена жанров задумана договорённостью, но сломана направлением ID, см. P1.
- В services/worker нет прямой записи user_anime.updated_at, reviews.updated_at и счётчиков topics. Scheduler вызывает функции БД и commit на согласованных интервалах 600/86400 секунд. Изменение synced_at у anime допустимо: это поле синхронизации, не триггерное updated_at списка/отзыва.
- Сервис списков/отзывов ещё не реализован в этом commit: реальный upsert UserAnime по составному PK проверить пока невозможно. Модель и SQL имеют правильный PK.
- Модели прочитаны; lazy, типы/nullable, ключи и индексы основных путей сопоставлены с SQL. Полная автоматическая проверка drift/autogenerate не проводилась. Чистое применение реальной миграции подтверждено на PG18, а не PG16.

### Что осталось и что согласовать

N1: фактические планы получены для всех сценариев; решение range вместо expression-индекса обосновано планами. N2: статическое ревью и целевые воспроизведения завершены, дефекты не исправлялись по запрету пользователя.

Перед завершением приёмки: повторить миграцию/SQL-проверки/планы/тесты на PostgreSQL 16 и целевом Python 3.12; согласовать с Фёдором две P1-ошибки worker, исправление фильтра годов и тестовую изоляцию/защиту DROP. После согласованных изменений прогнать регрессионные сценарии. Проверка реального AniList/Redis и конкурентного импорта не выполнялась. Масштабные выводы о быстродействии отложены до реального каталога; новая миграция сейчас не требуется.

Все результаты сохранены локально. Отправка Фёдору, создание issues/PR и коммитов не выполнялись. Изменения рабочего дерева ограничены docs/review-n1-n2-2026-11-06.md и docs/review-n1-n2-evidence/.
