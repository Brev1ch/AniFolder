## Антон (frontend) — интеграция этапов 3, 4, 6

Эндпоинты живы, готовы к подключению. По каждому блоку — что учесть.

### 1. Списки и профили (этап 3)

- `PUT /me/list/{anime_id}` — семантика полей: **пропущенное = не менять**,
  явный `"score": null` = **снять оценку**, прогресс сбрасывается явным
  `episodes_watched: 0`. Тип: `score?: number | null`. Ошибки: 409 нет
  (upsert всегда 200), 422 при `score` вне 1–10 и прогрессе больше числа
  эпизодов тайтла.
- `DELETE /me/list/{anime_id}` → 200 `{"ok": true}`; 404 `LIST_ENTRY_NOT_FOUND`,
  если записи не было.
- `GET /users/{username}` — добавить тип `UserProfile`: `stats.mean_score` —
  **строка** (`"7.5"`), как `avg_score`, не number.
- `GET /users/{username}/list` — элемент `UserListAnime`: поле `status` — это
  **статус списка** и оно затеняет статус тайтла (так и задумано по контракту).

### 2. Лента активности (этапы 3+4)

- Тип `ActivityItem` в `frontend/src/types/anime.ts` **моковый** — переписать
  под контракт. События: `list_added {status}`, `status_changed {from,to}`,
  `progress_updated {episodes_watched}`, `scored {score}` (`null` = оценка
  снята), `reviewed {review_id}`, `topic_created {topic_id}`,
  `commented {topic_id, comment_id}`. `anime` = карточка или `null`.
- Лента курсорная: `{items, next_cursor}`, `next_cursor = null` — конец.
  Курсор не парсить. Хук пагинации идентичен комментариям — переиспользовать.

### 3. Отзывы и сообщество (этап 4)

- `POST /anime/{id}/reviews` → 201. 409 `REVIEW_EXISTS` — показать «вы уже
  писали отзыв» и предложить редактирование (PATCH). PATCH меняет только
  переданные поля; пустой PATCH или `null` поля → 422.
- 403 `FORBIDDEN` — чужой отзыв. Кнопки редактирования/удаления показывать
  только автору (`user_id` в ответе).
- Темы: `comments_count` и `last_comment_at` приходят с сервера — **не
  считать на клиенте**.
- Комментарии: **новые первыми** (ранее договаривались иначе — устарело).
  `parent_id` — ответ на комментарий той же темы; чужая тема → 422.
- **Удалённый автор** во всех трёх сущностях: `username === "deleted_user"`,
  `user_id`/`author_id` = null. Отображать как «удалённый пользователь», не
  ломаться на null.

### 4. Совместимость вкусов (этап 6)

- `GET /users/{username}/compatibility` (только авторизованным):
  `{common_titles, compatibility}`. Значение −1…1, округлено до 2 знаков;
  `null` = меньше 5 общих оценок или все оценки одного одинаковые. Удобно в
  процентах: `Math.round((r + 1) * 50)`.

## Никита (БД)

1. **Планы запросов (N1-стиль, evidence)** для новых эндпоинтов —
   как `docs/review-n1-n2-evidence/`, но по текущему main:
   - список пользователя — индекс `(user_id, status, updated_at DESC)` + tiebreak `anime_id`;
   - лента активности — `(user_id, created_at DESC)` + курсорный фильтр `(created_at, id) < курсор`;
   - отзывы тайтла — `(anime_id, created_at DESC)`;
   - темы — оба индекса `(last_comment_at DESC)` и `(anime_id, last_comment_at DESC)`;
   - комментарии — `(topic_id, created_at)` + курсор;
   - совместимость — self-join `user_anime` (обе стороны по PK `(user_id, anime_id)`,
     фильтр `score IS NOT NULL`).
2. **Миграция `0002`** (`reviews.user_id` → NULL + `SET NULL`) — накатить на
   общий стенд. Осторожно: down-миграция удаляет сиротские отзывы (dev-only).
3. PostgreSQL 16 — целевая версия по конфигурации проекта; мои проверки шли
   на 14, финальную валидацию миграций и тестов делать на 16.
